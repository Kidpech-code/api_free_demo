🏗️ Go API Architecture Guide

คู่มือเชิงลึกสำหรับนักพัฒนา Backend ที่ต้องการเข้าใจโครงสร้าง API ระดับ production — ตั้งแต่หลักการ Clean Architecture ไปจนถึงการวิเคราะห์สถาปัตยกรรมจริงของ Uber ที่รองรับ 150 ล้าน reads/วินาที

ทำไมโครงสร้างถึงสำคัญ?

โปรเจกต์ที่โครงสร้างดีจะ:

  • อ่านง่าย — Developer ใหม่เข้าใจได้ภายใน 15 นาที
  • ทดสอบง่าย — แต่ละ layer mock ได้อิสระผ่าน interface
  • ขยายได้ — เพิ่ม feature ใหม่โดยไม่ทำลาย feature เดิม
  • เปลี่ยน technology ได้ — เปลี่ยน database จาก Redis เป็น PostgreSQL โดยแก้แค่ infrastructure layer
  • Deploy ได้มั่นใจ — Separation of concerns ทำให้ bug ไม่กระจาย

🧅 Clean Architecture

หลักการจาก Robert C. Martin (Uncle Bob) — แบ่ง code เป็นวงกลมซ้อนกัน โดย dependency ชี้เข้าด้านใน เสมอ (Outer layer รู้จัก Inner layer แต่ Inner layer ไม่รู้จัก Outer layer)

┌──────────────────────────────────────────────────┐ │ Delivery (HTTP/gRPC/CLI) │ ← รับ request จากโลกภายนอก │ ┌──────────────────────────────────────────────┐ │ │ │ Usecase (Business Logic) │ │ ← กฎทางธุรกิจ │ │ ┌────────────────────────────────────────┐ │ │ │ │ │ Domain (Entities + Interfaces) │ │ │ ← แก่นของระบบ │ │ └────────────────────────────────────────┘ │ │ │ └──────────────────────────────────────────────┘ │ │ Infrastructure (DB/Cache/External) │ ← implementation ที่เป็นรูปธรรม └──────────────────────────────────────────────────┘

หลักการสำคัญ 4 ข้อ

  1. Dependency Inversion — Domain กำหนด interface, Infrastructure implement → เปลี่ยน DB ได้โดยไม่แก้ business logic
  2. Separation of Concerns — Handler รับ HTTP request เท่านั้น ไม่มี business logic / Usecase ไม่รู้ว่ามา HTTP หรือ gRPC
  3. Single Responsibility — แต่ละ file/struct ทำหน้าที่เดียว เช่น auth_handler.go จัดการ auth endpoint, product_usecase.go จัดการ product logic
  4. Interface Segregation — interface เล็กและเฉพาะเจาะจง เช่น ProductRepository มีเฉพาะ method ที่ product ต้องการ

📁 Go Project Layout (Best Practice)

ตามแนวทาง golang-standards/project-layout ที่เป็นที่นิยมในชุมชน Go:

project-root/
├── cmd/                    ← Entry points (main packages)
│   └── api/
│       └── main.go         ← Binary entry — wire dependencies แล้วสั่ง start server
│
├── internal/               ← Private code (Go compiler ห้าม import จากภายนอก module)
│   ├── config/             ← Configuration loading
│   ├── domain/             ← Entities + Interfaces (แก่นของระบบ)
│   │   ├── model/          ← Data structures (Product, User, etc.)
│   │   ├── repository/     ← Repository interfaces
│   │   └── usecase/        ← Usecase interfaces
│   ├── usecase/            ← Business logic implementation
│   ├── infrastructure/     ← External service implementations
│   │   ├── repository/     ← DB/Cache implementation
│   │   ├── redis/          ← Redis client wrapper
│   │   ├── metrics/        ← Prometheus metrics
│   │   └── logging/        ← Structured logging (Zap)
│   └── delivery/           ← Transport layer
│       └── http/
│           ├── router.go   ← Route definitions + middleware chain
│           ├── handler/    ← HTTP handlers (controllers)
│           └── middleware/  ← Auth, rate limit, metrics
│
├── pkg/                    ← Public shared utilities (importable จาก project อื่น)
│   └── response/           ← Standardized JSON response
│
├── Dockerfile              ← Multi-stage build
├── go.mod                  ← Dependencies
└── railway.toml            ← Deployment config

ทำไมถึงใช้ internal/?

internal/ เป็น Go compiler enforcement — package ภายนอก module นี้ไม่สามารถ import code ใน internal/ ได้ ทำให้เรามั่นใจว่า business logic, repository, handler จะไม่ถูกเรียกใช้จากที่อื่นโดยไม่ตั้งใจ

ต่างจาก pkg/ ที่เป็น public — ใครก็ import ได้ เหมาะสำหรับ utility ทั่วไปเช่น response helper

ทำไมแยก domain/repository/ (interface) กับ infrastructure/repository/ (impl)?

นี่คือหัวใจของ Dependency Inversion Principle:

  • domain/repository/product_repository.go — กำหนด interface ProductRepository พร้อม method signatures
  • infrastructure/repository/product_repository.go — implement interface นั้นด้วย Redis
  • Usecase depend on interface (domain) ไม่ depend on implementation (infrastructure)
  • ถ้าวันนี้ใช้ Redis วันหน้าจะเปลี่ยนเป็น PostgreSQL → สร้าง infrastructure/repository/pg_product_repository.go ใหม่ โดย ไม่ต้องแก้ usecase เลย

🎯 Domain Layer — แก่นของระบบ

Domain layer คือ "ความจริง" ของระบบ — ไม่รู้จัก HTTP, ไม่รู้จัก Redis, ไม่รู้จัก Framework ใดๆ ทั้งสิ้น มีแค่ entities (structs) กับ interfaces (contracts)

Entity: Product

type Product struct {
    ID          string    `json:"id"`
    UserID      string    `json:"user_id"`
    Name        string    `json:"name"`
    Description string    `json:"description"`
    Price       float64   `json:"price"`
    Deleted     bool      `json:"deleted"`          // ← Soft Delete flag
    CreatedAt   time.Time `json:"created_at"`
    UpdatedAt   time.Time `json:"updated_at"`
}

สังเกตว่ามี Deleted bool — ใช้ Soft Delete pattern เหมือนของ Uber ที่ข้อมูลไม่หายจริง ยังค้นหาย้อนกลับได้

Repository Interface

type ProductRepository interface {
    Create(ctx context.Context, product *model.Product) error
    FindByID(ctx context.Context, userID, id string) (*model.Product, error)
    Update(ctx context.Context, product *model.Product) error
    SoftDelete(ctx context.Context, userID, id string) error
    HardDelete(ctx context.Context, userID, id string) error
    List(ctx context.Context, userID string, filter model.ProductFilter) (*model.ProductPage, error)
    Count(ctx context.Context, userID string) (int64, error)
    BulkCreate(ctx context.Context, products []model.Product) (int, error)
    BulkFindByIDs(ctx context.Context, userID string, ids []string) ([]model.Product, error)
}

ข้อสังเกต: นี่คือ interface ที่อยู่ใน domain layer — ไม่มี Redis, SQL หรือ implementation ใดๆ Usecase layer จะ depend on interface นี้ ไม่ใช่ depend on Redis implementation

Sentinel Errors

var (
    ErrNotFound   = errors.New("resource not found")
    ErrDeleted    = errors.New("resource has been soft-deleted")
    ErrForbidden  = errors.New("forbidden")
    ErrConflict   = errors.New("resource conflict")
    ErrQuotaLimit = errors.New("quota limit reached")
)

ใช้ errors.Is() เพื่อเปรียบเทียบ — เป็น Go idiom ที่สำคัญมาก handler layer จะใช้ errors นี้ตัดสินใจ HTTP status code

⚙️ Usecase Layer — Business Logic

Usecase layer คือที่อยู่ของ กฎทางธุรกิจ — validation, business rules, orchestration ระหว่าง repositories

Dependency Injection

type productUsecase struct {
    repo   repository.ProductRepository  // ← interface จาก domain
    logger *zap.Logger
}

func NewProductUsecase(
    repo repository.ProductRepository,
    logger *zap.Logger,
) usecase.ProductUsecase {
    return &productUsecase{repo: repo, logger: logger}
}

repo เป็น interface — ใน production จะเป็น Redis implementation แต่ใน test จะเป็น mock นี่คือพลังของ Dependency Injection + Interface

Business Logic ตัวอย่าง: Create Product

func (uc *productUsecase) Create(ctx context.Context, p *model.Product) error {
    // ── Validation (business rule) ──────────────
    if strings.TrimSpace(p.Name) == "" {
        return fmt.Errorf("product name is required")
    }
    if p.Price < 0 {
        return fmt.Errorf("price must not be negative")
    }

    // ── Quota check (business rule) ─────────────
    count, _ := uc.repo.Count(ctx, p.UserID)
    if count >= 50 {
        return domain.ErrQuotaLimit
    }

    // ── Delegate to repository (infrastructure) ─
    return uc.repo.Create(ctx, p)
}

Usecase ทำ 3 อย่าง: Validate → Apply business rules → Delegate ไม่เคยทำ HTTP response, ไม่เคยเรียก Redis โดยตรง

Auth Usecase: Dual-Token Flow

// Login Flow:
//  1. Validate credentials (sandbox: accept any user/pass)
//  2. Generate Access Token (JWT, HS256, 15 min TTL)
//  3. Generate Refresh Token (random hex, 7 day TTL)
//  4. Store refresh token in Redis HASH: sandbox:{user_id}:auth:refresh
//  5. Return TokenPair {access_token, refresh_token, expires_in}
//
// Why dual-token?
//  - Access Token: สั้น (15 min) → ถ้าหลุดเสียหายน้อย
//  - Refresh Token: ยาว (7 days) → ใช้ขอ Access Token ใหม่ได้
//  - เมื่อ Refresh → ทั้ง Access + Refresh ออกใหม่ (Token Rotation)

🔧 Infrastructure Layer — ของจริง

Infrastructure layer คือที่ implement interfaces ที่ domain กำหนด — ใช้ technology จริงๆ เช่น Redis, PostgreSQL, gRPC client

Redis DocStore Pattern

โปรเจกต์เราใช้ Redis เป็น primary data store (ไม่ใช่แค่ cache) — pattern ที่ Uber เรียกว่า DocStore

Redis Key Schema

Data key :  sandbox:{user_id}:product:{id}          → JSON string (ข้อมูลจริง)
Index key:  sandbox:{user_id}:product:_index         → ZSET (score=timestamp, สำหรับ pagination)
Cache key:  sandbox:{user_id}:product:_cache:{id}    → JSON string (hot-cache, TTL 5 min)

ใช้ 3 key types ร่วมกัน: Data (HASH), Index (ZSET), Cache (hot layer)

Read Path — Integrated Cache

  • 1
    Hot-Cache Lookup — ดึงจาก _cache:{id} key ก่อน (TTL 5 min) → Cache Hit
  • 2
    Storage Read — ถ้า cache miss → ดึงจาก data key sandbox:{uid}:product:{id} → Cache Miss
  • 3
    Back-fill Cache — เอาข้อมูลที่ได้เขียนกลับเข้า hot-cache → ครั้งต่อไปจะ hit cache (Write-Through)

Write Path — Write-Invalidate

// Update: เขียน data key ใหม่ + ลบ cache key (invalidate)
pipe := r.rdb.Pipeline()
pipe.Set(ctx, dataKey, data, r.dataTTL)    // overwrite data
pipe.Del(ctx, cacheKey)                     // invalidate cache
pipe.Exec(ctx)

// Soft Delete: เหมือน Update แต่ set Deleted=true + ลบออกจาก ZSET index
pipe.Set(ctx, dataKey, data, r.dataTTL)
pipe.Del(ctx, cacheKey)
pipe.ZRem(ctx, indexKey, id)               // ลบออกจาก index
pipe.Exec(ctx)

ทุก operation ใช้ Redis Pipeline — ส่งคำสั่งหลายตัวในรอบเดียว ลด network round-trips

Cursor-Based Pagination (ZSET)

// ใช้ ZSET score (unix nano timestamp) เป็น cursor
// ดีกว่า OFFSET/LIMIT ตรงที่:
//  - ไม่มีปัญหา "sliding window" เมื่อมีข้อมูลเพิ่ม/ลบ
//  - Performance: O(log N + M) ไม่ว่า page ไหนก็เร็วเท่ากัน

ids := r.rdb.ZRevRangeByScore(ctx, indexKey, &redis.ZRangeBy{
    Max:   "(" + cursor,   // exclusive upper bound
    Min:   "-inf",
    Count: limit + 1,      // +1 เพื่อเช็ค HasMore
})

Bulk Operations: Pipeline Magic

// BulkCreate: สร้าง 100 products ใน pipeline เดียว
pipe := r.rdb.Pipeline()
for _, product := range products {
    pipe.Set(ctx, dataKey, data, ttl)       // เก็บข้อมูล
    pipe.ZAdd(ctx, indexKey, redis.Z{...})  // เพิ่มเข้า index
    pipe.Expire(ctx, indexKey, ttl)         // ต่ออายุ index
}
pipe.Exec(ctx)  // ← ส่งทุกคำสั่งรวมกัน 1 round-trip!

// BulkFindByIDs: ใช้ 3 pipelines
// Pipeline 1: ลอง hot-cache ก่อน
// Pipeline 2: storage read สำหรับ cache miss
// Pipeline 3: back-fill cache สำหรับ miss ที่ read สำเร็จ

🌐 Delivery Layer — HTTP Interface

Delivery layer คือ "หน้าต่าง" ของระบบ — แปลง HTTP request เป็น usecase call แล้วแปลง result กลับเป็น HTTP response

Handler Pattern

func (h *ProductHandler) Create(c *fiber.Ctx) error {
    // 1. Parse input (HTTP concern)
    var req CreateProductRequest
    if err := c.BodyParser(&req); err != nil {
        return response.BadRequest(c, "invalid JSON body")
    }

    // 2. Extract user context (from middleware)
    userID := c.Locals("user_id").(string)

    // 3. Build domain model
    product := &model.Product{
        UserID:      userID,
        Name:        req.Name,
        Description: req.Description,
        Price:       req.Price,
    }

    // 4. Execute business logic (delegate to Usecase)
    if err := h.uc.Create(c.Context(), product); err != nil {
        // 5. Map domain errors to HTTP status
        if errors.Is(err, domain.ErrQuotaLimit) {
            return response.Err(c, 429, err.Error())
        }
        return response.InternalError(c, err.Error())
    }

    // 6. Return HTTP response
    return response.Created(c, product)
}

Handler ทำ 6 ขั้นตอน: Parse → Extract context → Build model → Delegate → Map errors → Respond

สังเกตว่า handler ไม่มี business logic — ไม่ validate price, ไม่เช็ค quota เอง — ปล่อยให้ usecase ทำ

Standardized Response Format

// ทุก endpoint ตอบกลับในรูปแบบเดียวกัน:
{
  "success": true,           // boolean: สำเร็จหรือไม่
  "data": { ... },           // ข้อมูล (ถ้าสำเร็จ)
  "error": "...",            // error message (ถ้าไม่สำเร็จ)
  "meta": {                  // pagination metadata
    "total": 42,
    "count": 20,
    "next_cursor": "...",
    "has_more": true
  }
}

ใช้ pkg/response package — helper functions: OK(), Created(), Err(), OKWithMeta()

Router Setup: Middleware Chain

// Route Groups with layered middleware:
api := app.Group("/api/v1")       // ทุก route เริ่มด้วย /api/v1

// Public routes — ไม่ต้อง auth
api.Post("/auth/login", authHandler.Login)
api.Post("/auth/refresh", authHandler.Refresh)

// Protected routes — ต้อง JWT
protected := api.Group("", middleware.JWTAuth(jwtSecret))

protected.Put("/products/:id", productHandler.Update)
protected.Delete("/products/:id", productHandler.Delete)

// Admin routes — ต้อง JWT + Role admin
admin := protected.Group("", middleware.RequireRole("admin"))
admin.Post("/products/bulk", productHandler.BulkCreate)

🚀 cmd/ & pkg/ — Entry & Shared

cmd/api/main.go — Dependency Wiring

ไฟล์ main.go เป็นที่ "wire" ทุกอย่างเข้าด้วยกัน (Manual Dependency Injection):

// ลำดับการ wire:
cfg      := config.Load()                              // 1. Config
logger   := logging.NewLogger(cfg.App.LogLevel, ...)    // 2. Logger

ทุกอย่าง inject ผ่าน constructor — ไม่มี global variable, ไม่มี init() function (ยกเว้น embed)

cmd/api/web.go — go:embed

//go:embed web

🏢 Uber CacheFront — 150 ล้าน Reads/วินาที

จากบทความ ByteByteGo: Uber ต้องรองรับผู้ใช้มือถือ 150+ ล้านคน ด้วยสถาปัตยกรรม 3 ชั้น

┌─────────────────────────────────────────────────────────┐ │ Mobile App / Client │ └──────────────────────────┬──────────────────────────────┘ │ ┌──────────────────────────▼──────────────────────────────┐ │ Query Engine (Microservices) │ │ reads/writes → standardized gRPC interface │ └──────────────────────────┬──────────────────────────────┘ │ ┌──────────────────────────▼──────────────────────────────┐ │ 🔥 CacheFront (Redis Cluster) │ │ • 150M+ reads/sec • 99.9% cache hit rate │ │ • Integrated Cache Layer — ส่วนใหญ่ตอบจาก Redis │ └──────────────────────────┬──────────────────────────────┘ │ (cache miss only) ┌──────────────────────────▼──────────────────────────────┐ │ Storage Engine (MySQL + DocStore) │ │ • Source of truth • Schemaless JSON storage │ │ • Sharded by partition key │ └─────────────────────────────────────────────────────────┘

Read Path ของ Uber

  • 1
    Client ส่ง request มาที่ Query Engine
  • 2
    Query Engine เช็ค CacheFront (Redis) ก่อน
  • 3
    ถ้า Cache Hit (99.9%) → ตอบกลับทันที ไม่ต้องไป DB
  • 4
    ถ้า Cache Miss (0.1%) → ไปอ่านจาก Storage Engine (MySQL)
  • 5
    เอาข้อมูลจาก MySQL เขียนกลับเข้า Redis (back-fill)

🛡️ Triple Cache Invalidation — ป้องกัน Stale Data

ปัญหาที่ยากที่สุดของ cache คือ "ทำยังไงให้ cache ไม่เก่า?" Uber ใช้ 3 ชั้นป้องกัน:

ชั้นที่ 1: TTL Expiration

ทุก cache key มี Time-To-Live — หมดอายุแล้วลบอัตโนมัติ เป็น safety net สุดท้าย

ชั้นที่ 2: Flux CDC (Asynchronous)

Change Data Capture — tail MySQL binlog → เมื่อ row เปลี่ยน → invalidate Redis key

ข้อเสีย: asynchronous → มี delay เล็กน้อย (มิลลิวินาที) ระหว่างเขียน DB กับ invalidate cache

ชั้นที่ 3: Write-Path Synchronous Invalidation

เมื่อเขียน DB สำเร็จ → invalidate cache ทันทีในขั้นตอนเดียวกัน (synchronous)

Uber ใช้ Soft Deletes + Monotonic Timestamps เพื่อตรวจจับ conditional updates:

  • Point Writes (INSERT/UPDATE/DELETE ที่รู้ key ชัดเจน) → invalidate ตรงๆ
  • Conditional Writes (UPDATE ... WHERE condition) → ก่อนหน้านี้ทำไม่ได้เพราะไม่รู้ว่า row ไหนโดนแก้ → แก้ด้วย soft delete + timestamp tracking

🔍 Cache Inspector — ตรวจสอบ Consistency

Uber สร้างระบบตรวจสอบอัตโนมัติ:

  1. รอ 1 นาที หลัง CDC event (ให้ทุก invalidation เสร็จ)
  2. อ่าน cache value ปัจจุบัน
  3. อ่าน DB value ปัจจุบัน
  4. เปรียบเทียบ — ถ้าไม่ตรง → alert + force invalidate

ผลลัพธ์: cache inconsistency ลดลงจาก ~0.05% → แทบเป็น 0%

🗄️ Redis DocStore — Deep Dive

มาดูรายละเอียดว่า Redis ถูกใช้เป็น primary data store อย่างไร

┌─ sandbox:user123:product:abc-123 ────────────────────────┐ │ (STRING) → JSON: {"id":"abc-123","name":"Laptop",...} │ └──────────────────────────────────────────────────────────┘ ┌─ sandbox:user123:product:_index ─────────────────────────┐ │ (ZSET) │ │ member: abc-123 score: 1719500000000000000 (nano ts) │ │ member: def-456 score: 1719500001000000000 │ │ member: ghi-789 score: 1719500002000000000 │ │ → ใช้ ZRevRangeByScore สำหรับ cursor pagination │ └──────────────────────────────────────────────────────────┘ ┌─ sandbox:user123:product:_cache:abc-123 ─────────────────┐ │ (STRING) → JSON copy with TTL=5min (hot-cache) │ │ → FindByID ดึงจากนี่ก่อน ถ้า miss ไปดึง data key │ └──────────────────────────────────────────────────────────┘

ทำไมต้อง ZSET Index?

Redis ไม่มี "SELECT * ORDER BY created_at" — ต้องสร้าง index เอง:

  • Score = Unix Nano Timestamp → เรียงลำดับตามเวลา
  • Member = Product ID → ชี้ไปที่ data key
  • ZRevRangeByScore → ดึง N items ที่ score น้อยกว่า cursor (newest first)
  • เมื่อ Soft Delete → ZRem(indexKey, id) ลบออกจาก index แต่ data key ยังอยู่

RBAC (Role-Based Access Control)

// Middleware chain สำหรับ admin-only routes:
middleware.JWTAuth(secret)        // 1. ตรวจ JWT valid หรือไม่ → 401 ถ้าไม่ valid
middleware.RequireRole("admin")   // 2. ตรวจ role claim → 403 ถ้าไม่ใช่ admin

// JWTAuth ใส่ค่าเข้า Locals:
c.Locals("user_id", claims["sub"])
c.Locals("role", claims["role"])

// RequireRole อ่านค่าจาก Locals:
role := c.Locals("role").(string)
if role != requiredRole {
    return response.Err(c, 403, "insufficient permissions")
}

ทำไมต้อง Dual-Token?

  • Access Token (JWT, 15 min) — stateless, server ไม่ต้อง lookup ใน DB ทุกครั้ง → เร็ว
  • Refresh Token (random hex, 7 days) — stateful, เก็บใน Redis → revoke ได้ทันที (logout = ลบจาก Redis)
  • Token Rotation — ทุกครั้งที่ refresh → ออก access + refresh ใหม่ทั้งคู่ → ลดความเสี่ยงถ้า refresh token หลุด
  • Constant-Time Comparison — ใช้ secureCompare() ป้องกัน timing attack ตอนเทียบ refresh token

Fixed Window Algorithm

Window: 1 นาที (60 วินาที)
Max: 60 requests/window

Timeline:
|------ Window 1 (12:00:00–12:00:59) ------|------ Window 2 (12:01:00–12:01:59) ------|

🐳 Deployment — Docker + Railway

Multi-Stage Dockerfile

# ── Stage 1: Build ──────────────────────────────────
FROM golang:1.25.1-alpine AS builder
WORKDIR /build
COPY go.mod go.sum ./
RUN go mod download                    # cache dependencies
COPY . .
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -trimpath -ldflags="-s -w" \
    -o /app/server ./cmd/api/

# ── Stage 2: Runtime ────────────────────────────────
FROM scratch                           # ← smallest possible image
COPY --from=builder /etc/ssl/certs/ /etc/ssl/certs/
COPY --from=builder /app/server /app/server
ENTRYPOINT ["/app/server"]

ข้อดีของ Multi-Stage Build:

  • Image เล็กมาก — FROM scratch = 0 byte base image, binary เดียว ~15 MB
  • Security — ไม่มี shell, ไม่มี package manager → attack surface แทบเป็น 0
  • CGO_ENABLED=0 — static binary, ไม่ depend libc → ทำงานบน scratch ได้
  • -trimpath -ldflags="-s -w" — ลบ debug info + path info → binary เล็กลง
  • go:embed — HTML/CSS/JS อยู่ในส binary ไม่ต้อง COPY แยก
